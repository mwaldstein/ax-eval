# ax-eval Project Audit — 2026-07-18

## Scope and method

Six parallel review passes over the full repository (~19.4k lines of Rust), one per dimension: architecture/CLI surface, agent adapter layer, run pipeline/process execution, evaluation/judge, scenario/fixture/discovery, and tests/CI/docs/roadmap. High-severity findings were re-verified against the source. The document was then adversarially reviewed by three independent models against the codebase — gpt-5.3-codex and gemini-3.1-pro (both via opencode) and the codex CLI — and their verified corrections are incorporated. Findings were also cross-checked against TODO.md and `docs/tradeoffs.md` so that already-planned or explicitly-accepted items are labeled as such. File references are current as of commit `4d2e223`.

## Executive summary

ax-eval is in good structural health: clean module boundaries, disciplined error propagation (production panics are limited to infallible static-regex construction — e.g. `src/adapter/claude_code/normalize.rs:49`, `src/evaluation/gates/assertions.rs:146`, `src/transcript/analyzer.rs:37` — plus one dead-code timestamp helper), clippy/fmt-clean, unusually strong test hygiene (help-snapshot tests, mock-driven fixture regression tests, ADR discipline), and an actively worked roadmap. The audit found no architectural rot, though the run-interruption lifecycle and redaction are cross-cutting debt.

The significant problems cluster in three areas, all fixable without redesign:

1. **Evaluation integrity.** The headline `first_try_success_rate` is mathematically distorted, all three adapters count missing exit codes as successes, and a skipped judge silently zeroes the composite score. For a measurement tool, wrong numbers are the worst failure mode.
2. **Data-safety gaps.** Secret redaction misses nearly all persisted output, and result paths are built from unsanitized names.
3. **Paid runs on invalid premises, or with no record.** Failed setup still launches the agent; auth checks can't fail for two of three adapters; several failure paths discard a completed (paid) run without writing any record.

## Priority 0 — Evaluation integrity, data safety, wasted spend

### 1. Metric integrity: the scores themselves are distorted
- **`first_try_success_rate` is mathematically wrong.** `src/interaction_profile.rs:53-66` counts unique commands that succeeded on first occurrence but divides by *total* command count: five invocations of one always-successful command yield 0.2 despite zero failures. It feeds `efficiency_component` in the composite (`src/eval_helpers.rs:22`; default weight 0.10, `src/eval_helpers.rs:11`), and it is the headline efficiency metric in reports. Relatedly, `retry_count = total − unique` (`src/interaction_profile.rs:48`) counts benign repetition (e.g., polling `status`) as retries, and `iteration_ratio` already encodes unique/total. **Fix:** make numerator/denominator consistent and split "repeat after failure" from "repeat after success." This changes reported numbers — flag it in the CHANGELOG.
- **Missing exit codes default to success in all three adapters.** claude-code backfills absent tool-result exit codes with `0` (`src/adapter/claude_code/normalize.rs:269-271`), and codex and opencode do the same (`src/adapter/codex/normalize.rs:70`, `src/adapter/opencode/normalize.rs:111`), inflating first-try success and deflating error counts whenever the agent's output omits an exit code.
- **A skipped judge silently zeroes the composite.** `compute_composite_score` uses `judge_score.unwrap_or(0.0)` (`src/eval_helpers.rs:14`), so a gate-failure skip or `--no-judge` run scores as if the judge awarded zero while the weights still assume a judge ran. Human-readable reports do say "judge not run" (`src/transcript/writer.rs:27,352`), but `EvaluationMetrics` carries no structured skip reason — `--no-judge` and gate-failure skip both collapse to `judge_score: None`. **Fix:** renormalize weights when the judge is absent and add a structured skip reason to the metrics record.

### 2. Secret redaction misses the places secrets actually land
`redact_sensitive` is applied in exactly two places (`src/transcript/writer.rs:218,273`): the echoed setup-command string and gate-detail messages in `report.md`. It is never applied to `transcript.raw.txt`, `transcript.human.txt` (generated from unredacted raw content in `write_raw`, `src/transcript/writer.rs:63`), `tool-output.raw.txt`, `events.jsonl` (full stdout/stderr of setup/execution/post-scripts), `run.json`, or judge feedback in `evaluation.md` — command *output*, where an echoed API key would actually appear. The redaction patterns themselves are also narrow. Results directories are the artifact users share.

**Fix:** route all artifact writes through a single redaction-aware sink so new output types can't bypass redaction by construction; broaden the pattern set.

### 3. Paid runs on invalid premises — auth and setup
- **Auth detection is decorative.** claude-code and opencode adapters hardcode `authenticated: true` when `--version` succeeds (`src/adapter/{claude_code,opencode}/mod.rs:16-22`), so a logged-out CLI fails deep inside a paid run instead of at the availability check. Codex infers auth solely from `OPENAI_API_KEY`, misreporting users authenticated via `codex login` (`src/adapter/codex/mod.rs:28`).
- **Failed setup still launches the agent.** A non-zero exit from a setup command sets `setup_success = false` and *continues* (`src/run/setup.rs:135-142`); the lifecycle proceeds to `run_attempt` and finalize only prints a warning (`src/run/records.rs:120-122`). The agent runs — and spends credits — against a broken environment, producing a polluted interaction profile. **Fix:** short-circuit before `run_attempt` when setup fails, recording a failed run.

### 4. Completed (paid) runs can vanish without a record
Three failure paths discard a run that has already incurred cost or setup work, instead of finalizing a failed record:
- A **timeout in setup or health-check** is harness-side, not paid agent execution, but it still propagates as a hard error before `metrics.json`, `report.md`, or the `results.db` record are written — leaving a prepared results directory with no record (unlike a non-zero setup exit, which is at least recorded).
- An **agent timeout** is a paid-run failure: it propagates from `run_attempt` before `persist_execution_transcript` runs (`src/run/execution.rs:115-121`), losing all partial evidence; timeouts also never reach metrics since `completed` is derived solely from `exit_code == 0` (`src/run/execution.rs:153`).
- An **evaluation error after the paid agent run** propagates via `?` (`src/run/execution.rs:152-166`) and skips DB finalization entirely — the repo's own regression test codifies this (`src/run/tests.rs:441`, "bubbles_evaluation_failure_without_record").

**Fix:** treat these uniformly — persist whatever evidence exists and finalize a failed/cancelled record on every post-spend failure path.

## Priority 1 — Robustness and correctness

- **Cache key is incomplete: judge config and agent version.** `CacheKey` (`src/results/types/cache_key.rs`) hashes scenario YAML, prompt, fixture contents, tool *name*, and model. Two things are missing: (a) the CLI-level `--judge-model`/`--judge-tool`/`--no-judge` overrides (`src/cli.rs:77-87`) — scenario-YAML judge config *is* covered via the scenario hash — so a cached run silently returns its old judge verdict under different judge settings; (b) the resolved agent CLI *version*, so a user who upgrades their agent CLI and re-runs with `--cache` gets served results from the old version — and comparing agent versions is a core use case for this tool. Caching is opt-in (`--cache`), which is the only mitigation. **Fix:** fold effective judge configuration and the adapter's `--version` string into the key.
- **Result paths are built from unsanitized names.** `get_results_dir` (`src/run/utils.rs:35-43`) sanitizes `model` but concatenates both `tool` and `scenario_name` raw; a name containing `/` or `..` writes outside `ax-eval-results/`, and the directory is planned and created before adapter-name validation runs (`src/run/mod.rs:48`, `src/run/lifecycle.rs:35`). Same trust-boundary family: file gates join gate paths onto the workspace root unchecked (`src/evaluation/gates/file.rs:6`), so a scenario can assert against `../` paths outside the fixture, and `template_folder` accepts arbitrary relative/absolute paths (`src/fixture.rs:19-41`). Threat model today is a local YAML author (foot-gun, not attack vector), but discovery-generated and shared scenario packs are on the roadmap. **Fix:** apply `safe_segment` (already used by discovery, `src/discover/batch.rs:18`) in `get_results_dir`; canonicalize gate and template paths against an allowlist of roots — note discovery intentionally rewrites `template_folder` to absolute paths under its output tree (`src/scenario/discovery.rs:32-36`), so "fixtures root only" would break it.
- **Token/cost capture is incomplete.** `token_usage` is never populated for claude-code even though its `stream-json` output emits a `usage` object alongside the `total_cost_usd` that *is* parsed; codex has tokens but never `cost_usd`. Cross-tool token/cost comparisons — headline README features — silently under-report. **Fix:** parse the missing fields; add a per-adapter self-test asserting they're non-`None` where the upstream CLI emits them.
- **Timeout kill leaks child processes.** Kills signal only the immediate `sh -c` child, not its process group (`src/session.rs:162-167`, `src/command_execution.rs:93-114`); backgrounded processes survive. Spawn in a new process group and kill the group.
- **No Ctrl-C handling.** An interrupted run leaves a partial results dir, no `results.db` entry, and possibly live children. A minimal handler should flush a "cancelled" record and best-effort kill the child process group.
- **`sh -c` everywhere vs. claimed Windows support.** Setup/health-check use `run_shell_with_session` and scripts delegate to `run_shell_piped`, both hardcoding `sh -c` (`src/command_execution.rs:34-59`, via `src/script_runner.rs:124`). On plain Windows without Git Bash/WSL, every scenario using scripts fails outright. Either dispatch to `cmd`/PowerShell on Windows or scope the README claim.
- **Scenario field typos are silently ignored.** No scenario/gate/judge struct uses `#[serde(deny_unknown_fields)]`, so `teir:` instead of `tier:` is a silent no-op (`src/scenario/types.rs`). Given the otherwise excellent "did you mean X?" validation UX, this is an easy consistency win — and pairs with TODO.md's existing "better YAML parse error messages" item. Likewise, `validate` never checks that `template_folder` exists (`src/scenario/validation.rs:203-304`), though it does existence-check rubric paths.
- **Judge invocation has no retry.** A single transient judge-CLI failure aborts the whole evaluation after a full (paid) scenario run (`src/evaluation/judge.rs:145-151`). Add 1-2 bounded retries. (Composite-weight sums are already validated as a warning, `src/scenario/validation.rs:278-288`; consider promoting to a hard error to match rubric weights, which fail at load.)
- **Symlinks in templates mishandled.** `copy_dir_recursive_with_exclusions` (`src/run/utils.rs:9-29`) uses `DirEntry::file_type()`, so symlinks are neither `is_dir()` nor `is_file()` and are **silently skipped** entirely; the fixture hash also skips non-file entries (`src/run/cache.rs:55-57`), so copy and hash actually agree about symlinks — both ignore them. The hardcoded `"scenarios"` exclusion also silently drops any template subdirectory with that name.
- **Corrupt cache entries are silent misses.** Cache `get` swallows unreadable/corrupt JSON via `.ok()?` (`src/results/cache.rs:69-70`) with no integrity warning and no cache schema version.

## Priority 2 — Enhancements

- **Multi-run variance.** Nothing in the evaluation/results path aggregates across runs; every score is presented as if n=1 were ground truth, and the LLM judge is non-deterministic. An `--iterations N` mode with mean/variance reporting would materially strengthen the tool's core credibility claim. TODO.md already lists "statistical significance testing across runs" and `ax-eval compare` under Future — this audit's recommendation is to elevate that work, since it protects the tool's central promise. Until then, the judge's `confidence` field — parsed but never persisted to `metrics.json` or used in scoring — could at least flag low-confidence verdicts in output.
- **`results.jsonl` is unsafe under concurrent writers.** `ResultsDB::append` uses plain `OpenOptions::append` with no file locking (`src/results/db.rs`); records exceeding the atomic-write size can interleave and corrupt the line-oriented DB if two runs write simultaneously. Low urgency today (single-process CLI), but TODO.md lists "parallel scenario execution" as a Future item — advisory locking is a prerequisite for that work, so it belongs in that work package.
- **Cross-platform CI.** CI lint/test/build runs on Linux only; macOS/Windows exist only as unverified release-build targets (`.github/workflows/ci.yml:12`). A test-only matrix job would make the README's platform claim verified rather than aspirational (and would have surfaced the `sh -c` issue).
- **Real recorded transcripts as adapter fixtures.** Normalizer tests use hand-authored synthetic JSON; the recent opencode judge-parsing bug is exactly the class of failure real captured transcripts would catch. Check in 1-2 real transcripts per adapter — a natural companion to MCP Stage 4, which touches all three normalizers. Also record the agent CLI version (already captured by `--version`) into run metadata — this doubles as the cache-key version input above.
- **`schema_version` field for scenarios.** No versioning exists in the YAML schema; adding an optional field defaulted to `1` now creates a forward-compat detection point before the schema is widely adopted (pairs with the MCP schema work in ADR-0005).
- **Sandboxing posture.** The agent process runs with the user's full credentials and network access. This is a *documented, accepted* tradeoff (`docs/tradeoffs.md` — fixture isolation is file-level only, with an opt-in sandboxed runner named as future direction), so the remaining gap is discoverability: the README never mentions it, and users sharing scenario packs will hit it cold. A one-line README pointer to the tradeoffs doc closes that cheaply.
- **Dry-run summary cosmetics.** Dry-run records used to set a misleading successful guardrail roll-up with empty metrics (`src/run/records.rs:59`); they are in-memory only and never reach the DB (`src/run/lifecycle.rs:59`; test at `src/run/tests.rs:433`), so the impact was limited to a slightly misleading CLI summary line. Use a distinct "dry run" status instead.
- **Housekeeping.** Global judge config (already in TODO.md); consolidate `Result<T, String>` in `src/config.rs` and gate assertions onto `anyhow`/`thiserror` per AGENTS.md's own convention; extract the duplicated `AX_EVAL_ENABLED` consent block in `main.rs:168-176,232-240`; split templates/color helpers out of the 625-line `commands.rs`; remove unused `ToolModelArgs` (`src/cli.rs:23`); fix AGENTS.md:65's reference to a `specs/` directory that doesn't exist in the repo; add a CONTRIBUTING.md; consider a results-retention/prune option since every run permanently retains a full fixture copy. (Note: `--dry-run` for `discover` was considered and is already struck in TODO.md as infeasible — discovery inherently requires LLM calls.)

## Strengths worth preserving

- Layered, well-tested command execution (PTY → piped fallback, bounded waits, timeout classification) and properly opt-in caching with fixture-content hashing.
- Defensive adapter parsing — no panics on malformed agent output, per-tool normalizers isolated behind a small `ToolAdapter` trait.
- Author UX in validation: Levenshtein "did you mean" suggestions, line-number hints, thorough `long_about` help text with copy-pasteable examples.
- Documentation discipline (ADRs, CONTEXT.md, `docs/tradeoffs.md` for accepted limitations, per-fixture regression tests, CLI-help snapshot tests) well above the norm for a project this size.
